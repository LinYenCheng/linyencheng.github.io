一、Implementation Plan：抗失憶的狀態機與存檔點

在實際開發（或大規模養豬）過程中，你一定遇過這種令人崩潰的場面：

結果 AI 又要重新讀檔案、重新掃描專案、猜測昨天的進度。這不僅是極大的 Token 資源浪費，更讓整個專案陷入失控風險。

Implementation Plan（實作計畫 / 養豬日誌）不只是拿來「開工前畫藍圖」，更是拿來「中斷後恢復 Context」的 Checkpoint 存檔點！

flowchart TD
    Goal["人類場長給定目標 (Goal)"] --> Plan["產出 Implementation Plan 日誌"]
    Plan --> Exec["施工實作"]
    Exec --> Interrupt["(中斷 / 隔天開工)"]
    Interrupt --> Reload["讀取 Plan Checkpoint 存檔點"]
    Reload --> Next["精準繼續執行 Next Steps"]
    Exec --> Verify{"驗證 Inspection"}
    Verify -- 失敗 --> Plan
    Verify -- 通過 --> Done["交付完成 (Done)"]

一份能當作 Checkpoint 的標準 Plan，必須包含 5 大欄位：

  1. 為什麼要動這區？（Goal & Scope / Non-goals）：明確劃定邊界，告訴 AI「今天只修 A 區門鎖，不要順便把 B 區的牆給拆了」。
  2. 會拆到哪些豬舍？（Files to Change）：動手前列出受影響檔案清單，人類場長簽字後才許開工。
  3. 怎麼知道豬有養好？（Verification Checklist）：客觀驗證指標（如 npm test、單元測試）。
  4. 今天處理到哪？（Progress Checkpoint）：記載 [x] 進度，隔天開工一秒載入狀態。
  5. 當時為什麼這樣決定？（Decisions & Notes）：記錄「為什麼選甲飼料不選乙飼料」，防止 AI 隔天失憶又選錯。

二、養豬第一原則：先在 AI Studio 養一隻試試看

真正有經驗的豬農，絕對不會一開始就：買地 ➔ 蓋 1,000 頭豬舍 ➔ 買 1,000 隻豬 ➔ 開始祈禱。
比較合理的做法是：先養一隻。

確認飼料配方對不對？通風好不好？流程真的養得活？
在把 Prompt、Tool 與 Logic 硬編碼進正式專案前，Google AI Studio 就是最完美的「實驗沙盒」：

flowchart TD
    Sandbox["Google AI Studio (實驗豬舍沙盒)"]
    Sandbox --> Step1["實驗 Prompt 與 System Instructions"]
    Step1 --> Step2["定義 JSON Schema (Structured Output)"]
    Step2 --> Step3["測試 Function Calling 工具呼叫"]
    Step3 --> Verify["驗證工作流成功 (原型豬存活)"]
    Verify --> Prod["搬入 Production 正式專案 (大規模養豬場)"]

⚠️ 關鍵工程警訊：Schema 正確 ≠ 業務內容正確

請千萬記住這個核心原則：

這段 JSON 完全符合 Schema 定義，但如果 P001 實際上只有 82 公斤，這隻豬已經在 JSON 裡被 AI 養爆了！XD

真正的工程驗證防線應該是：
Gemini ➔ Structured Output ➔ Schema Validation ➔ Business Rule Validation ➔ 進入產線

三、Google Sheets：輕量 MVP 外部記憶與 Data Pipeline

很多工程師會想：「我要做 AI Agent，先來研究 PostgreSQL、API Gateway、Redis 還有 Kubernetes……」結果三個月過去了，Agent 連個影都沒看到。

養豬不能只靠 AI 記住：Context 不是 Database！
每天產生的數據需要持久化儲存。對於小型 Prototype 與內部驗證來說，Google Sheets + Google Apps Script (GAS) 是成本最低、速度最快的選擇：

    Gemini["Gemini Agent<br>(Structured Output)"] -->|HTTP POST| GAS["Google Apps Script<br>(Web App)"]
    GAS -->|appendRow| Sheet["Google Sheets<br>(試算表資料庫)"]
    Sheet -->|讀取歷史紀錄| Analysis["歷史數據回讀 / 趨勢分析"]

⚠️ 關鍵 Guardrail：AI 不是獸醫

在實際生產環境中，千萬不能把 Gemini 的建議直接當成專業醫療診斷。標準架構應具備分級防線：

    AI --> Human["人工確認處置 (Human-in-the-Loop)"]

五、如果這不是 Demo，而是一座真的 AI 智慧養豬場？

想像一下，早上 06:00，養豬場開始一天的工作。第一個起床的不是我，而是 Agent 團隊：

  1. 06:00｜Sidecar 背景自動化啟動：實時採集溫度、濕度、自動電子秤體重、攝影機巡檢畫面與飼料投放量。
  2. 06:05｜MCP 把真實世界接進 Agent：透過 MCP Protocol，AI 伸向實體感測器與控制設備。
  3. 06:10｜Agent 自動巡場與數據分類：P001 正常、P002 增重停滯、P004 體溫過高。
  4. 06:15｜Subagents 分工協作：主 Agent 自動指派任務給「健康分析小豬」、「成長數據小豬」與「環控小豬」。
  5. 06:20｜人類角色登場 (Human-in-the-Loop)：手機響起推播——「今日巡檢完成。997 隻小豬健康正常；2 隻需觀察；1 隻體溫偏高需人工確認。」我喝一口手沖咖啡，走到特定豬舍前進行最後確認。
flowchart TD
    Goal["業務需求 (Goal)"] --> Boss["主 Agent (Farm Boss)"]
    Boss --> Plan["/plan 狀態機藍圖"]
    Plan --> Sub["Subagents 平行開發與審查"]
    Sub --> Hooks["Hooks & Rules 連鎖卡關"]
    Hooks --> Deploy["自動化驗證與部署"]
    Deploy --> Sidecar["Sidecar 24h 背景監控維運"]

Google AI 生態系大總結

技術元件在 AI 自動化產線中的核心定位
Gemini核心大腦：負責高階意圖理解、邏輯推理與決策支援
Google AI Studio實驗沙盒：低成本快速 Prototype Prompt、JSON Schema 與 Function Calling
Antigravity / Agy CLIAgentic Coding：專案級語境感知與命令列終端機執行引擎
AGENT.md / Rules最高管理規章：界定 Agent 思考邊界與程式碼風格防線
Skills & Plugins能力擴充包：將常用工具與工程 SOP 模組化打包帶走
MCP外部世界連接器：連通 Sensor、GitHub、Database 與外部 API
Subagents團隊分工：上下文隔離的專業小豬機器人
Sidecars背景維運：24 小時不間斷的事件收集與定時排程
GAS + Sheets輕量 MVP 資料庫：最低成本持久化記錄歷史數據

結語：我到底要不要轉職養豬？

回到第 1 天我問自己的那個問題：「要轉職養豬，還是做被取代的工程師？」

寫完這系列，我的答案拆解為兩個層面：

  1. 我要不要離開工程領域？
    不要。 因為這段旅程讓我深刻體會到：AI 越強大，能將模糊需求轉化為嚴謹 Data Contract、架構邊界與驗證防線的工程師就越不可或缺。工程師的價值從未消失，只是往上移到了架構層。
  2. 我要不要去養豬？
    如果真要養豬，我也絕對不會是盲目買 100 隻豬的傳統豬農；而是選擇第三條路：工程能力 × AI × IoT × 養豬！

    Boss["🧑‍🌾 我 (Farm Manager)"] --> TeamA["🤖 AI Agent 團隊 A 區"]
    Boss --> TeamB["🤖 AI Agent 團隊 B 區"]
    TeamA --> BarnA["🐷 智慧豬舍 A 區"]
    TeamB --> BarnB["🐷 智慧豬舍 B 區"]

或許未來的某一天，我真的會站在竹東老家附近的某座實體養豬場裡，身邊圍繞著一群高效運作的 Agent 團隊。

那時我打開手機預覽介面，畫面顯示：

我喝一口手沖咖啡，笑一笑：
「嗯……這套 AI 雙刀流工作流，好像還真有點搞頭！」 🐷☕

常見問題 FAQ

Q1：在小專案中導入這套流程會不會過度繁瑣？

可以採取漸進式導入：初期僅需 AGENT.md 與 /plan 指令即可獲得顯著的品質提升；當專案擴大或需要背景維運時，再逐步引入 Hooks、Subagent 與 Sidecar。

Q2：Google Sheets 當資料庫能支撐多久？

Google Sheets 僅作為 Prototype 與概念驗證（MVP）時期的輕量過渡方案。當資料量突破數萬筆或需要高併發交易時，應順暢切換為 Cloud SQL 或 PostgreSQL 等正式關聯式資料庫。

Q3：AI Software Factory 最終會完全取代人類嗎？

不會。AI 負責執行、計算與平行化雜活，而核心的需求定義、價值判斷、架構邊界設定與重大風險決策（Human-in-the-Loop），始終需要工程師的專業判斷。
