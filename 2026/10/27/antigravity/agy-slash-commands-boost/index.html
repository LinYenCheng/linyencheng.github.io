Agy 互動指令（Interaction Modes & Slash Commands） 是指在 Google Antigravity 開發環境 中，透過特定前綴斜線指令（如 /plan、/grill-me、/goal、/boost）動態切換代理人思考深度與行為模式的控制技術。工程師無須死記冗長 Prompt，即可依據當下開發階段切換角色：第一步透過 /grill-me 與 /plan 釐清架構；第二步使用 /goal 進行無中斷自主推進；遭遇分散式併發難題時，則啟用 /boost 自動調度三層推理階層。

在上一篇文章中，我們學會了如何靠 Subagent 派出偵察豬、品管豬與獸醫豬進行非同步平行分工。

但當手邊的軟體專案演變成跨模組架構重構，或是遇到極度棘手的 Concurrency、演算法漏洞與長流程任務時，你很快會發現一個新困惑：

「每次都要由我來手動決定派哪隻小豬機器人、怎麼拆解任務、怎麼追蹤進度，那我豈不是變成天天打卡調度的基層工頭了嗎？！」

如果今天的 Subagent 已經會分工幹活，那 AI 自動化的下一步會是什麼？

答案是：未來有一天，小豬機器人肯定可以做得比你老闆還要好！
我們正在從「人類手動分工」，跨越到**「AI 開始幫我管理 AI」**的 Agent Team 未來範式！

一、AI 自動化的終極演化軸線

回顧我們一路探索的抽象層級，AI 輔助開發的進化路徑清晰可見：

flowchart TD
    P["Prompt ➔ 手動輸入指令，問一答一"] --> A["Agent ➔ 具備自主能力，幫你執行 Tool & Code"]
    A --> S["Subagent ➔ 人類手動指派專業小豬機器人（人類管理分工）"]
    S --> B["Multi-Agent / Boost ➔ AI 自己組建深度推理階層系統"]
    B --> T["Agent Team / Teamwork ➔ AI 自主拆解專案、自動派工與驗證（AI 管理分工）"]

Subagent 是我開始學會分工；Agent Team 則是 AI 開始學會自我管理分工！

二、進入深度推理階層：/boost

當你遇到單一 Agent 思考容易陷入死胡同的複雜演算法、併發死鎖（Deadlock）或大型重構時，Antigravity 推出的 /boost 模式開創了三層式的 Multi-Agent Reasoning Hierarchy：

flowchart TD
    O["Orchestrator (主導調度者)"]
    O --> D1["DeepCoder (代碼與邏輯推理 Agent)"]
    O --> D2["DeepInvestigator (調查與架構分析 Agent)"]
    D1 --> W["Execution Workers (背景平行執行與驗證小豬工人)"]
    D2 --> W

/boost 的核心思維變革

你不再需要費心指定「哪隻小豬做什麼」，你只需要把最難的題目丟給系統：

「這題 Concurrency 排程很難，你自己組一個推理團隊來處理。」

/boost 會在數秒到數分鐘的互動中，自動調度 Orchestrator 進行任務解構、派發 DeepCoder/DeepInvestigator 做邏輯演繹，最後由 Execution Workers 進行測試與驗證。

三、大型專案自主協同：/teamwork-preview

如果說 /boost 是處理「高難度單點問題」的智囊團，那麼 /teamwork-preview 則是處理「大型長流程軟體工程」的完整團隊。

官方將 /teamwork-preview 定位為讓一組專門化的 Agent 自主協同大型專案、多檔案重構與複雜調研的機制：

sequenceDiagram
    autonumber
    actor Boss as 人類場長 (工程師)
    participant Platform as /teamwork-preview 平台
    participant Planner as 需求與 Milestone 拆解組
    participant Team as 平行開發小豬群
    participant QA as 獨立測試驗證組

    Boss->>Platform: 提供 High-Level Goal (例如：將 REST API 全面升級為 GraphQL)
    Platform->>Planner: 拆解為 Milestone 清單並召喚對應 Agent
    Planner->>Team: 平行派工與實作
    Team->>QA: 提交變更並進行獨立測試
    QA-->>Platform: 自動整合與驗證結果
    Platform-->>Boss: 交付可合併成果

人類只需要給出一個 High-Level Goal，剩下的 Milestone 拆解、小豬機器人召喚、平行實作與獨立驗證，全部由 Agent Team 自行協調完成！

四、三代機制對比表：Subagent vs Boost vs Teamwork

比較維度👷 Subagent (手動小豬機器人)🚀 /boost (深度推理團隊)🤝 /teamwork-preview (專案團隊)
核心精神「幫我做這件指定的具體工作」「這題很難，你自己深入思考」「幫我完成這個大型專案目標」
主導角色人類場長親自手動分派系統自動組建三層推理階層平台系統自動組織 Agent Team 運作
適合規模小～中型獨立子任務複雜 Bug、演算法、併發與難題重構大型多檔案重構、跨模組長流程專案

五、養豬場派工思維：七大免費 Slash Commands

看完了頂規的 /boost 與 /teamwork-preview，很多人可能會問：
「是不是一定要開滿 Multi-Agent 團隊，AI 自動化才管用？」

不要看到頂規就興奮，免費的基本功才是每天真的會用到的！

在 Antigravity 中，最常用、也最能拉開工程師生產力差距的，是那些免費且看似不起眼的 /command。官方將其定位為 Interaction Modes（互動工作模式）。讓我們用「養豬場派工思維」來理解：

flowchart TD
    Q["我現在到底想叫 AI 做什麼？"] --> M1["想清楚再動手<br>(/plan, /grill-me)"]
    Q --> M2["直接衝到底不要停<br>(/goal)"]
    Q --> M3["背景協助不打斷<br>(/browser, /btw)"]
    Q --> M4["沉澱經驗與排程<br>(/learn, /schedule)"]

模式一：讓 AI「想清楚再動手」

  1. /plan ➔ 蓋新豬舍前先出建築藍圖核心精神：先盤點受影響檔案，產出施工藍圖，人類 Review 簽字後才許開工。
  2. /grill-me ➔ 豬農反過來考問場長核心精神：在動手前，AI 先嚴肅反問你：「你到底要養幾隻？要肉豬還是母豬？清糞便的管道你想過沒？」把模糊需求挖乾淨。

模式二：讓 AI「直接幹，不要停」

  1. /goal ➔ 豬農自己把整批豬照顧完核心精神：進入自主推進迴圈直到驗證通過，不會每改一個檔案就停下來等確認。

模式三：讓 AI「背景幫忙，不要打斷我」

  1. /browser ➔ 派會走路的小豬巡視豬舍核心精神：沙盒化 Chrome 瀏覽器 Subagent，獨立進行 DOM 檢視與排版截圖。
  2. /btw ➔ 「欸 BTW，那隻豬放在哪？」核心精神：帶外查詢（Out-of-band Query），快速解答突發小問題，完全不會打斷主工作流！

模式四：讓 AI「留下經驗，明天自動上班」

  1. /learn ➔ 把養豬教訓寫進管理手冊核心精神：將除錯教訓自動萃取為 .agents/rules/，下次不再犯！
  2. /schedule ➔ 設定定時自動餵豬機核心精神：建立週期性任務，直接銜接 Sidecar 背景維運機制。

🔗 終極絕招：Command Chaining (指令連鎖)

Antigravity 支援在同一個 Prompt 前連鎖串接多個指令：

這會形成一條無懈可擊的產線：

flowchart LR
    G["/grill-me<br>(先問清楚需求)"] --> P["/plan<br>(產出實作計畫)"]
    P --> GO["/goal<br>(自主執行到底)"]
    GO --> B["/browser<br>(UI 畫面檢驗)"]
    B --> L["/learn<br>(沉澱規則手冊)"]
    L --> S["/schedule<br>(定期巡檢)"]

結語：我到底還算不算在「寫程式」？

如果有一天，我只需要對著終端機說一句：

「幫我把這個產品做出來，並部署上線。」

然後 AI 自己決定找 Research 小豬搜競品、Developer 小豬寫 Code、Testing 小豬跑測試、Security 獸醫豬掃漏洞，甚至自己成立 Team 自動開會排時程……

那我到底還算不算在「寫程式」？
還是……我其實已經正式轉職成豬場老闆了？ 🐷老闆！

常見問題 FAQ

Q1：/plan 產出的計畫若有遺漏，該如何微調？

直接在對話中針對該 Plan 提出修訂意見（例如：「請加入對既有 Session 儲存機制的相容性檢查」）。Agent 會更新 Artifact 文件，確認內容完整後再下達執行指令。

Q2：使用 /boost 會不會大幅增加等待時間？

是的。/boost 會啟動深層推理迴圈與多重假設交叉比對，回應時間可能從數十秒至數分鐘不等。建議將其保留給真正棘手的架構痛點，而非一般 CRUD 功能。

Q3：什麼情境最適合使用 /btw？

當主 Agent 正在進行耗時幾分鐘的長流程重構，而你突然需要確認某個型別名稱或常數數值時，使用 /btw 可以在完全不干擾主任務的前提下取得答案。
